Every claim cites `file:line` read in the installed packages, relative to each package's root
(`three:` = `three@0.187.0/node_modules/three`, `cc:` = `camera-controls@3.1.2.../dist/camera-controls.module.js`).

Two outside sources, kept only where the code confirms them: Utsubo "100 Three.js Tips" (U#n = tip n;

## 1. Imports and the lazy chunk
- Import named symbols from `three`, never `import * as THREE`. The entry re-exports from `three.core.js` (three:build/three.module.js:6-7) and only `src/nodes/**` has side effects (three:package.json:25-27), so a bundler can drop the rest.
- Addons are per-file paths (`three/addons/*`, three:package.json:15-16); take only what runs (`mergeGeometries`: three:examples/jsm/utils/BufferGeometryUtils.js:156).
- The renderer is the weight: WebGL entry 133,691 B, `three/webgpu` 221,519 B (slice-7 §4, measured there, not by me; entry at three:package.json:18). The first screen has its 173 KiB cap: three, camera-controls and the scene live in one dynamic `import()` chunk, loaded after the text (ARCHITECTURE "React"), and a phone loads it only on "View in space".
- camera-controls has no `import` of three (cc has none) and takes it by `CameraControls.install({ THREE: subset })` (cc:314); pass the subset the typings list (Vector2/3/4, Quaternion, Matrix4, Spherical, Box3, Sphere, Raycaster; cc readme:~110-125). Without `install` it fails at first use (the `THREE` variable is set only there, cc:315).
- No worker and no WebAssembly in three's core: no `new Worker`, `createObjectURL` only in `LoadingManager` (three:src/loaders/LoadingManager.js:189), no `WebAssembly` in `src/`. `KTX2Loader` starts a worker from a Blob URL (three:examples/jsm/loaders/KTX2Loader.js:342,347); its transcoder uses WebAssembly (slice-7 §3; not re-read by me). Never import it.

## 2. Creating the renderer
- Defaults: `antialias=false`, `alpha=false`, `powerPreference='default'`, `preserveDrawingBuffer=false`, `stencil=false`, `depth=true`, `failIfMajorPerformanceCaveat=false` (three:src/renderers/WebGLRenderer.js:76-84).
- `antialias:true` is the browser's MSAA on the default framebuffer (WebGLRenderer.js:3725). Reason to be wary: render targets (shadow maps, composer) default to `samples: 0` (three:src/core/RenderTarget.js:41,72), so MSAA does not follow into a composer chain (inferred). Choose by tier: on for High on desktop, off on touch and Low.
- `powerPreference` is a hint to the browser (WebGLRenderer.js:3728). ARCHITECTURE wants the low-power GPU: pass `'low-power'` (U#74 says `'high-performance'`: écarté, it burns battery for a mostly idle scene).
- Pixel ratio: `setPixelRatio` resizes the buffer (WebGLRenderer.js:642-648). Cap it (2 desktop, as U#80, since a Retina screen drawn at 1.25 is blurred and 8 ms a frame leaves room; the Auto probe drops a slow device; 1 touch, Low 1 and 0.8). Use `setSize(w, h, false)` so three does not write the canvas style (WebGLRenderer.js:673). A pixel ratio change also moves the point-size scale (see 7).
- `alpha:false` gives an opaque buffer (clear alpha 1, WebGLRenderer.js:3722); the scene is near-black space, so keep it opaque.
- Context loss: three listens to `webglcontextlost` / `webglcontextrestored` on the canvas (WebGLRenderer.js:405-406), calls `preventDefault`, sets a flag, and `render()` returns at once while lost (WebGLRenderer.js:1117-1124, 1659 region); on restore it re-runs `initGLContext` and keeps the shadow and info settings (1127-1141). So: add your own listener (abortable) to show the list on loss and to ask one frame on restore. Tests use `forceContextLoss()`/`forceContextRestore()`, which need `WEBGL_lose_context` (WebGLRenderer.js:609-625). U#98 and W's device-loss doc agree; for WebGPU see 14.

## 3. Colour (one image grade)
- Working space is linear (three:src/math/ColorManagement.js:22); `outputColorSpace` defaults to sRGB (WebGLRenderer.js:313).
- A `Texture` has `colorSpace = NoColorSpace` unless told (three:src/textures/Texture.js:48). Colour maps (Earth day, clouds, star sprites, anything seen as colour) must be `SRGBColorSpace`: 8-bit sRGB textures get an `SRGB8_ALPHA8` internal format, so the GPU decodes them (three:src/renderers/webgl/WebGLTextures.js:237). Data maps (normal, roughness, masks, noise, LUTs) stay `NoColorSpace`. The colour space is in the texture's cache key (WebGLTextures.js:606): set it before the first render.
- `ImageBitmapLoader` forces `colorSpaceConversion: 'none'` (three:src/loaders/ImageBitmapLoader.js:181) and ignores `flipY`/`premultiplyAlpha` on the texture (Texture.js:274,286; WebGLTextures.js:980-982): set those in the loader options (ImageBitmapLoader.js:73,95), and tag the colour space yourself.
- Tone mapping is off by default, exposure 1.0 (WebGLRenderer.js:278,286). It is applied only to materials with `toneMapped` and only when drawing to the screen, not into a render target (WebGLRenderer.js:2414-2423; three:src/renderers/webgl/WebGLPrograms.js:181-187; Material.js:458). With a composer, finish with `OutputPass`, which carries tone mapping and colour conversion (three:examples/jsm/postprocessing/OutputPass.js:15-24); U#76 says the same.
- Changing `toneMapping` makes a new program variant (WebGLRenderer.js:2550); `toneMappingExposure` is a plain uniform (WebGLRenderer.js:2762), free to change. Set the tone mapper once at creation, before any compile, then tune exposure only. Candidates exist: `NeutralToneMapping` (Khronos, three:src/constants.js:476-483), AgX (473), ACES (455). Which looks right is a design-reviewer call against the frames (NV).
- A custom `ShaderMaterial` must include `<tonemapping_fragment>` and `<colorspace_fragment>` like the points shader does (three:src/renderers/shaders/ShaderLib/points.glsl.js, fragment), or its colours skip the grade.

## 4. The frame loop on demand (60, 30, 10, 0)
- `setAnimationLoop(cb)` starts a `requestAnimationFrame` chain; `onAnimationFrame` requests the next frame before calling `cb` (three:src/renderers/webgl/WebGLAnimation.js, `onAnimationFrame`; WebGLRenderer.js:1613-1617). So skipping work inside `cb` still wakes the page at display rate: 30 and 10 fps must come from your own scheduler (a `requestAnimationFrame` or timer you start, and cancel at 0 fps), not from an early return in a three loop.
- Own the loop (ADR: one loop, owned by the scene): `render()` only when a reason exists (input, `controls.active`, moving bodies, a flight, a texture arrived), pick the next rate from the reason, and stop (`setAnimationLoop(null)` stops and cancels, WebGLAnimation.js `stop`; or never start one). U#64-65/R3F `frameloop="demand"` is the same idea, with no R3F here.
- Hidden or covered: stop the loop on `visibilitychange` and on your covered signal, and restart with a fresh delta. `Timer` has `connect(document)` for the Page Visibility API (three:src/core/Timer.js:12,43-53). `Clock` is deprecated since r183 (three:src/core/Clock.js:6,61; U#100): use `Timer`. camera-controls' own readme still shows `THREE.Clock`; ignore it.
- A hidden tab throttling `requestAnimationFrame` is browser behaviour (NV in source): do not rely on it for the 0 fps goal.
- `renderer.render` does nothing while the context is lost (WebGLRenderer.js:1659 region), so no extra guard is needed there.

## 5. Memory
- `dispose()` must be called on: every `BufferGeometry` (three:src/core/BufferGeometry.js:1464), every `Material` (three:src/materials/Material.js:1226; it only dispatches the event, so its textures are NOT freed), every `Texture` (three:src/textures/Texture.js:675), every `WebGLRenderTarget` (three:src/core/RenderTarget.js:493; render-target textures are freed by it, `Texture.dispose` on them does nothing, Texture.js:667-671), every `LightShadow` (three:src/lights/LightShadow.js:297-311; a removed light leaves its shadow map), every composer and pass (`EffectComposer.dispose`, three:examples/jsm/postprocessing/EffectComposer.js:354-359; `UnrealBloomPass` disposes its 5+ targets, UnrealBloomPass.js:212-214), `InstancedMesh.dispose` (three:src/objects/InstancedMesh.js:396-410: its buffers only; geometry and material stay yours), `BatchedMesh.dispose` (three:src/objects/BatchedMesh.js:1542-1565: it disposes its geometry). Removing an object from the scene frees nothing: "geometries, materials and textures ... must be disposed of separately" (three:src/core/Object3D.js:1671-1672).
- One owner per resource, a registry per part (ARCHITECTURE); a texture shared by many materials is disposed once by its owner, and disposing it removes it for every user (shared GPU object, see 10).
- `ImageBitmap`: three never calls `close()` (the only `close()` in `src/` is a stream controller, three:src/loaders/FileLoader.js:187; U#38 agrees). Close a bitmap after upload, in `texture.onUpdate` (called after upload: Texture.js:344, WebGLTextures.js:1461). Risk, inferred: after a context restore the texture re-uploads from its image, which a closed bitmap cannot supply; keep the URL and reload on restore.
- `renderer.info`: `memory.geometries` and `memory.textures` count what is on the GPU now (up at upload, down at delete: three:src/renderers/webgl/WebGLGeometries.js:54,67; WebGLTextures.js:465,538,814,2090,2148; render-target attachments count as textures, there is no render-target counter); they never reset. A resource counts only after its first use, so take the baseline after one full render of everything. `info.programs` lists compiled programs (WebGLRenderer.js:486). `info.render` (`calls`, `triangles`, `points`, `lines`) resets at the start of every `render()` when `autoReset` is true (WebGLRenderer.js:1744; three:src/renderers/webgl/WebGLInfo.js:52-58); `frame` is not reset (WebGLInfo.js:11). With several `render()` calls per frame (composer) set `autoReset=false` and call `reset()` yourself (WebGLRenderer.js:540-556), or the draw count is the last pass only. This is the measurement for "flat draw count" and "baseline after 20 flights" (U#30,37,94).
- Never freed by itself: the context. `renderer.dispose()` frees three's caches and stops the loop but does not lose the context or remove the canvas (WebGLRenderer.js:1088-1113); call `forceContextLoss()` (609) first if the canvas goes away. Also never freed: event listeners on the canvas you added, controls (see 13), `ImageBitmap`s, object URLs, a `FinalizationRegistry` entry is only for ids (three:src/renderers/webgl/WebGLGeometries.js:8).

## 6. Many objects at a flat draw count
- `InstancedMesh`: one draw for `count` instances (`renderInstances`, WebGLRenderer.js:1341-1343). `count` is writable (InstancedMesh.js:84): draw fewer than allocated, sorted by distance, and the draw bound is the cap, not the list. Matrices are a `Float32Array(count*16)` (InstancedMesh.js:57); set `needsUpdate` after writes (InstancedMesh.js:52), use `setUsage(DynamicDrawUsage)` for what changes, and `addUpdateRange` to upload a part (three:src/core/BufferAttribute.js:108,189).
- Frustum culling of an instanced mesh is ONE test of its bounding sphere (Frustum.js:148-152), computed once when null and cached (InstancedMesh.js:151-176; "you may need to recompute ... if an instance is transformed", 149). Instances moved or recentred without `computeBoundingSphere()` are culled by a stale sphere (they vanish); or set `frustumCulled=false` for the one big field. The compute is O(count): do it once per recentre, not per frame. No per-instance culling: cull in `core/lod` and write only the visible instances.
- `BatchedMesh`: different geometries, one draw, needs `maxInstanceCount`, `maxVertexCount` up front (BatchedMesh.js:197); per-object frustum culling and sorting are on by default (216, 226) and cost CPU per instance each frame (1572-1666): turn off what you do not need. (U#32's "per-instance opacity r183" not found in `BatchedMesh.js`: écarté.)
- Static meshes: merge with `mergeGeometries` (BufferGeometryUtils.js:156) per material, and set `matrixAutoUpdate=false` on static objects (Object3D.js:253,450,1188; U#34). Share materials (U#33; one program, fewer state changes).
- `LOD` swaps whole objects by distance, with `hysteresis` against flicker (three:src/objects/LOD.js:116) and `autoUpdate` (83). It is per object: right for the few near bodies, wrong for 10,000 far ones (use instanced points/billboards).
- Draw count, not triangle count, is what the bench holds flat; read it from `info.render.calls` (U#30: about 100 on mobile; NV as a target).

## 7. Points and stars
- `PointsMaterial.size` is in pixels and capped by the GPU's `ALIASED_POINT_SIZE_RANGE` (three:src/materials/PointsMaterial.js:95-103). Uniform size is `size * pixelRatio`, scale `height * 0.5` (three:src/renderers/webgl/WebGLMaterials.js:307-308); attenuation divides by `-mvPosition.z`, perspective cameras only (points.glsl.js vertex, `gl_PointSize *= scale / -mvPosition.z`). `sizeAttenuation` defaults true (PointsMaterial.js:111). A star that must not shrink to nothing far away: `sizeAttenuation=false` with your own per-point size attribute and a floor.
- Points are square by default: the stock fragment shader never reads `gl_PointCoord` unless a `map` is set (three:src/renderers/shaders/ShaderChunk/map_particle_fragment.glsl.js:10). Round and crisp: a small soft `alphaMap` (PointsMaterial.js:93) or a `ShaderMaterial` that shapes alpha from `gl_PointCoord` (keep the two includes of section 3). `alphaToCoverage` smooths edges but needs MSAA (Material.js:402-405).
- Glowing stars: `depthWrite=false` (Material.js:222-231), `transparent=true` (124), `blending=AdditiveBlending` (three:src/constants.js:133). Additive makes order irrelevant, so no sorting dependence.
- Sorting is per object, not per point: the list sorts by `renderOrder`, then by the object's bounding-sphere centre depth, back to front for transparent (three:src/renderers/webgl/WebGLRenderLists.js:7-13; WebGLRenderer.js:1935-1950). Its cost is the number of transparent objects, so few `Points` objects with many points, never one object per star. Inside one `Points` the buffer order is the draw order (inferred).
- A `Points` is culled by its geometry's bounding sphere: compute it from the real extent, or the sky blinks.

## 8. Transparency, rims, glow, post-processing
- Transparent objects cost sorting and overdraw and break instancing batches; keep them few and give each a `renderOrder` (Object3D.js:327). An atmosphere rim is a slightly larger shell with `side: BackSide` (Material.js:88), additive, `depthWrite=false`: its cost is fill rate at the planet's size on screen, so drop it when the body is small (inferred).
- Glow without a blinding bloom: a soft additive shell or sprite with a falloff, bounded alpha, `toneMapped` as the grade requires; no scene-wide bloom. Selective bloom: NV.
- `EffectComposer` is expensive by construction: two full-size `HalfFloatType` targets at `size * pixelRatio` (EffectComposer.js:66-69, 300-301), one extra full-screen draw per pass, `samples: 0`. `UnrealBloomPass` adds 5 mips of horizontal and vertical targets starting at half size (UnrealBloomPass.js:99-120) and needs renderer tone mapping on (its doc, UnrealBloomPass.js:~22-23). Budget: no composer on Low and touch; if used, half-size passes (U#80, NV measured).
- U#73 (pmndrs/postprocessing) is a new dependency: écarté (Stop and ask). U#82: `PostProcessing` is deprecated since r183, `RenderPipeline` replaces it (three:src/renderers/common/PostProcessing.js:5), relevant only if WebGPURenderer is chosen.

## 9. Shadows
- Off by default (`shadowMap.enabled=false`, `autoUpdate=true`, `type=PCFShadowMap`: three:src/renderers/webgl/WebGLShadowMap.js:84-89). Map size defaults to 512 x 512 per light (LightShadow.js:104) and is clamped to `maxTextureSize` (WebGLShadowMap.js:180-195). Memory grows with the square of the size; point lights use a cube target (WebGLShadowMap.js:~245; the "six draws per object" of U#54 is NV).
- With `autoUpdate=true` the depth pass reruns every frame; with `autoUpdate=false` it runs only after `needsUpdate=true`, which three resets itself (WebGLShadowMap.js:88-89, 378; U#61). Our scene is mostly still: set `autoUpdate=false` and request one update when the lit world, the light or the camera's focus changes.
- One light for one close world: only the world seen close alone casts and receives (`castShadow` / `receiveShadow`, Object3D.js:299,307); every other body has both false. Dispose its `light.shadow` when leaving (LightShadow.js:297-311).
- Changing `shadowMap.type` recompiles every material (WebGLShadowMap.js:132-134): choose once. `PCFSoftShadowMap` is removed in this version and falls back to `PCFShadowMap` with a warning (WebGLShadowMap.js:97-103; constants.js:73-75; U#61). `VSMShadowMap` makes all receivers cast (constants.js:79-84): refuse it.

## 10. Textures
- Anisotropy is 1 unless set (Texture.js:838), applied as `min(anisotropy, max)` (WebGLTextures.js:760-764), max read from the extension (three:src/renderers/webgl/WebGLCapabilities.js:16). Planet surfaces seen at grazing angles want 4 or 8 (the max is device-dependent: read it, do not hard-code). Raise anisotropy before resolution (U#27).
- `generateMipmaps` is true (Texture.js:257) and runs `generateMipmap` on upload (WebGLTextures.js:1455), on the main thread at the first render that uses the texture. A 4096 x 2048 WebP also decodes to 4 B per pixel plus a third for mips (slice-7 §4 computes ~89 MB for two; not measured; U#37's 64/85 MiB for 4096^2 agrees). Three has no byte counter.
- Upload happens at first use, so a flight stalls: call `renderer.initTexture(texture)` ahead (WebGLRenderer.js:3622-3627). Images larger than `maxTextureSize` are resized through a canvas (WebGLTextures.js:49-79): size the WebP for the Low tier yourself.
- Decode off the main thread: `ImageBitmapLoader` (three:src/loaders/ImageBitmapLoader.js:8-13,181) with options set before load; then wrap in a `Texture`, set `needsUpdate`, `colorSpace`, `generateMipmaps` (wrapping details: NV).
- One `Texture` object on many materials is one GPU texture (properties are per texture; the GPU texture is keyed by the parameters list, WebGLTextures.js:585-606). `Texture.clone()` shares the `source` (Texture.js:483-499). Cache by URL (U#40), refcount, dispose once; plan: released after five minutes covered.
- KTX2: refused (section 1; U#22 écarté). Mipmaps stay on (U#27).

## 11. Shaders
- `compile(scene, camera, targetScene)` builds the programs of every mesh, points, line and sprite in `scene`, visible or not (`scene.traverse`, WebGLRenderer.js:1400-1498), using the lights of `targetScene` (visible ones only, 1412-1426): set lights, fog, shadow settings and tone mapping first (doc, 1387-1393), or the program differs from the one used at render.
- `compileAsync` resolves when programs are ready, using `KHR_parallel_shader_compile` if present, else polling every 10 ms (WebGLRenderer.js:1519-1566). Call it for the destination world's scene (its `targetScene` = the live scene) before the flight ends, then await it; U#5 agrees (its "r184 non-blocking" note is about WebGPU, Renderer.js:1019).
- A program variant also depends on output colour space and tone mapping, and on drawing to a render target or the screen (WebGLRenderer.js:2334-2353, 2414-2420): warm up the same way you render.
- `onBeforeCompile` exists for `WebGLRenderer` only (Material.js:520-531). Its default `customProgramCacheKey` is `onBeforeCompile.toString()` (Material.js:544-547) and goes into the program key (WebGLPrograms.js:445): two materials patched by the same function text share a program even if the closure's values differ. Return a key that names every value baked in the shader text; prefer uniforms to defines so planets share one program.
- Many planets, one program: vary look through uniforms and textures, not through new shader text (inferred from the key).

## 12. Precision far from the origin
- Object transforms are JS doubles (`Matrix4.elements` is a plain array: three:src/math/Matrix4.js:86), and `modelViewMatrix` is built on the CPU as camera-inverse times world (WebGLRenderer.js:2173). But geometry positions and `instanceMatrix` are `Float32Array`s (InstancedMesh.js:57), applied before the model-view (three:src/renderers/shaders/ShaderChunk/project_vertex.glsl.js). Float32 loses detail far from the mesh origin (GL uniforms are float32 by spec; not three).
- So render camera-relative (plan §5): keep the camera at the origin, store world positions in doubles in `core`, and each frame or on each recentre write `world - camera` into the instance matrices and point attributes, then recompute the bounding sphere (section 6). Cost is O(drawn bodies), bounded by the ladder. Test at a far coordinate (plan §5).
- `logarithmicDepthBuffer` writes `gl_FragDepth` in every fragment (three:src/renderers/shaders/ShaderChunk/logdepthbuf_fragment.glsl.js) and "disables the Early Fragment Test ... decrease in performance" (WebGLRenderer.js:3731-3732): off by default; use it only if near/far tuning fails. `reversedDepthBuffer` is the faster, more accurate option, needs `EXT_clip_control`, and makes the log buffer ignored (WebGLRenderer.js:3732-3736, 3757; U#48): test `capabilities.reversedDepthBuffer`, never assume.
- Near and far: `PerspectiveCamera` defaults are near 0.1, far 2000 (three:src/cameras/PerspectiveCamera.js:33). Set them per place (galaxy, system, close world) from the camera's distance, and change them with `updateProjectionMatrix()` (call name from memory of the API: NV here). "Depth precision depends more on near" (U#48) : not checked in source, so écarté as a rule, kept as a tuning hint.

## 13. camera-controls
- `update(delta)` computes the pose and returns true when a render is needed (cc:2095-2100, 2288-2300); it takes seconds, uses `smoothDamp` (time-based, cc:79-100) and divides by `deltaTime` on overshoot (cc:96): pass a real, positive delta from `Timer`.
- On demand: setters set `_needsUpdate` (e.g. cc:1184, 1239, 1741) and nothing happens until you call `update`. Call `update` in your loop only while there is a reason; keep going until the `sleep` event, which fires only inside `update` (cc:2262-2286). Events: `controlstart`, `control`, `controlend`, `transitionstart`, `update`, `wake`, `rest`, `sleep` (cc:1305-1312); `active` is `!_hasRested` (cc:1215-1217). `wake` and `controlstart` are the signals to start the loop.
- Defaults: `smoothTime` 0.25 s, `draggingSmoothTime` 0.125 s, `restThreshold` 0.01 (cc:427,432,481). "Sleep usually fires a few seconds after the camera appears to have stopped" (cc:1312): the loop runs those seconds at 60 or 30 fps, a cost to budget.
- Transitions: `setLookAt(..., enableTransition)` with `false` by default snaps (cc:1731); with `true` it returns a promise that resolves on the `rest` event (cc:2574-2586), which only `update()` dispatches (cc:2276-2282). A stopped loop leaves the promise pending forever, and `dispose()` removes all listeners (cc:2386-2392), so a pending flight never settles: race it with an `AbortSignal` and never `await` it without the loop running. `stop()` jumps current state to the target (cc:2029-2034).
- Reduced motion: none built in (no `prefers-reduced-motion` in `cc`): use `enableTransition=false` and crossfade in the overlay; no idle orbit, nothing calls `update` while at rest.
- Dispose: `dispose()` = `removeAllEventListeners()` + `disconnect()` (cc:2386-2392); `disconnect()` cancels, removes the DOM listeners (cc:2371-2380) including `pointermove` on the document (cc:721-723) and the wheel handler (cc:797), and restores the element's `touchAction`/`userSelect`. It does not touch the camera. Leave `colliderMeshes` empty (4 raycasters per update, cc:484-487). Peer range `three >=0.126.1` (cc package.json:46-47), tested on 0.178 (line 41): 0.187 is outside what it was tested against; the gate's journeys are the proof.

## 14. WebGL2 against WebGPURenderer at 0.187
- `WebGLRenderer` is WebGL 2 only (a WebGL 1 context throws, WebGLRenderer.js:101-104; `getContext('webgl2')`, 411-413).
- `WebGPURenderer` (`three/webgpu`) tries WebGPU, else falls back to a WebGL2 backend, or `forceWebGL: true` forces it (three:src/renderers/webgpu/WebGPURenderer.Nodes.js:25-37; W, U#2,8). The fallback costs: the 221 KB entry (plan), an async `init()` before any render (three:src/renderers/common/Renderer.js:899; W: `await renderer.init()`), a `setAnimationLoop` that awaits it (Renderer.js:2387-2389), node materials, and no `onBeforeCompile` (Material.js:520-531; TSL instead, W). Whether a given `ShaderMaterial` or the `examples/jsm` composer runs on it: NV. Device loss: `onDeviceLost` (Renderer.js:689; WebGPUBackend.js:266; WebGL backend `webglcontextlost`, WebGLBackend.js:246).
- Decision input: the plan's shaders are WebGL GLSL (points, rims, program keys, composer). Choosing WebGPURenderer means rewriting them in TSL. Alexis chose `WebGLRenderer` for the demo; moving later means rewriting them.

## 15. Testing
- No GL needed (pure JS): `Vector3`, `Matrix4` (Matrix4.js:86), `Frustum.intersectsObject` (Frustum.js:146-166, with a geometry and no renderer), `Sphere`, `Box3`, `Color`, `Spherical`, `Timer`, `BufferGeometry`, `mergeGeometries`, and an `InstancedMesh` (its constructor only fills typed arrays, InstancedMesh.js:37-104). `core/*` stays free of GL so Vitest covers it.
- Needs a browser with WebGL2: `new WebGLRenderer` (a canvas through `createElementNS`, three:src/utils.js:146-150, then `getContext('webgl2')` and a throw if none, WebGLRenderer.js:411-423), compile, `info`, context loss, anything with a texture upload.
- A software renderer (SwiftShader class) can prove: the scene renders without errors, `info.render.calls` and `info.memory` are what the code claims (they are JS counters, WebGLInfo.js), disposal returns the counters to baseline, context lost and restore with `forceContextLoss` where `WEBGL_lose_context` exists, the CSP listener sees no violation, a canvas is not blank.
- It cannot prove: 60 fps on a phone, real GPU memory, point-size caps, `reversedDepthBuffer`/anisotropy limits, parallel compile timing, thermal behaviour (plan §6: bench with CPU slowed 4x on real hardware; the canvas is not pixel-compared).

## Ten mistakes to refuse in review
1. `import * as THREE from 'three'` or any three import reachable from the first screen's chunk.
2. A `setAnimationLoop` callback that returns early to "throttle" (the page still wakes at display rate).
3. `await controls.setLookAt(..., true)` with no loop running or no abort path (the promise never settles).
4. A colour texture left at `NoColorSpace`, or a data map tagged `SRGBColorSpace`.
5. `dispose()` on a mesh or a material expecting its geometry or textures to go, or a shared texture disposed twice by two owners.
6. Moving or recentring instances without `computeBoundingSphere()` (or `frustumCulled=false`), or one `Points`/`Mesh` object per body.
7. A new `ImageBitmap` never closed, or closed before a context restore could re-upload it.
8. `shadowMap.autoUpdate` left true, a second shadow-casting light, `VSMShadowMap`, or a changed `shadowMap.type` after first render.
9. `logarithmicDepthBuffer` or a composer/bloom turned on without a measured need, or `KTX2Loader`/any worker or WebAssembly path.
10. A first-time shader compile during a flight (no `compileAsync` of the destination's real scene, lights and tone mapping first), or a draw-count bench read after `info` autoReset hid multi-pass calls.
